# پله (Pelleh) — پلتفرم مزایده معکوس خرید و تأمین کالا

اسکلت اولیهٔ پروژه: Next.js 14 (App Router) + TypeScript + MongoDB/Mongoose +
Tailwind CSS. صفحهٔ اصلی مطابق طرح ارسالی ساخته شده و ساختار داده/API برای
منطق اصلی کسب‌وکار (مزایده، مخفی‌سازی هویت فروشنده، انتخاب برنده، تأیید
دوطرفهٔ تحویل) آماده است. **پرداخت و کیف‌پول عمداً از این فاز حذف شده‌اند**
و می‌توانند بعداً به‌عنوان یک ماژول جدا اضافه شوند.

## اجرا روی سیستم شما

اگر قبلاً یک‌بار `npm install` ناقص زده‌اید، اول پوشه‌های قدیمی را پاک کنید
تا نصب از صفر و تمیز انجام شود:

```bash
rm -rf node_modules package-lock.json
npm install
cp .env.example .env.local   # مقدار واقعی MONGODB_URI و AUTH_SECRET را اینجا بگذارید
npm run seed                  # پایگاه‌داده را با دیتای نمونه پر می‌کند
npm run dev
```

نیازمندی: Node.js نسخه ۱۸.۱۷ به بالا (فایل `.nvmrc` هم برای این منظور اضافه شده).

پس از seed، با این حساب‌های آزمایشی می‌توانید وارد شوید (رمز همه: `password123`):

| نقش | ایمیل |
|---|---|
| خریدار | `buyer@pelleh.ir` |
| فروشنده | `seller1@pelleh.ir` (و `seller2@pelleh.ir`, `seller3@pelleh.ir`) |
| ادمین | `admin@pelleh.ir` |

## وضعیت اتصال به دیتابیس

**همه‌ی صفحات الان مستقیماً از MongoDB می‌خوانند** — دیگر هیچ mock data ای
در پروژه نیست. لایه‌ی `lib/queries.ts` نقطه‌ی مرکزی همه‌ی کوئری‌هاست و
قانون «فقط RFQهای status:'active' در لیست عمومی دیده شوند» را همان‌جا
اعمال می‌کند تا هیچ صفحه‌ای نتواند اشتباهی آن را دور بزند.

**دکمه‌های «انتخاب فروشنده» و «تایید تحویل» کاملاً کار می‌کنند:**
- در صفحه‌ی هر RFQ، اگر شما خریدار و مالک آن باشید، کنار هر پیشنهاد باز
  دکمه‌ی «انتخاب این پیشنهاد» می‌بینید (`SelectBidButton` →
  `POST /api/rfq/[id]/select`).
- بعد از انتخاب، برای خریدار و فروشندهٔ برنده یک پنل «تایید تحویل» ظاهر
  می‌شود (`DeliveryConfirmPanel` → `POST /api/rfq/[id]/delivery`)؛ با
  تایید هر دو طرف، RFQ به `completed` می‌رود.
- تا قبل از انتخاب، در همان صفحه فقط قیمت و توضیح پیشنهادها دیده می‌شود؛
  نام/شهر فروشنده اصلاً در پاسخ سرور وجود ندارد (نه فقط مخفی در ظاهر).

## محافظت از مسیرها

`middleware.ts` مسیرهای `/profile`, `/seller`, `/admin`, `/rfq/new` را
می‌پوشاند: بدون ورود به `/login` هدایت می‌شوید، و هرکدام فقط برای نقش
مرتبط (خریدار/فروشنده/ادمین) باز است.


## منطق کسب‌وکار پیاده‌سازی‌شده

1. **خریدار درخواست خرید (RFQ) ثبت می‌کند** — دسته‌بندی، مقدار، استان/شهر
   (لوکیشن یک فیلتر اصلی است، نه فرعی).
2. **فروشندگان روی آن قیمت پیشنهاد می‌دهند.** تا وقتی RFQ باز است
   (`status: 'active'`)، هویت فروشنده هرگز به خریدار فرستاده نمی‌شود —
   این فیلتر در خودِ API انجام می‌شود (`/api/rfq/[id]/bids`)، نه فقط در UI.
3. **خریدار یک پیشنهاد را انتخاب می‌کند** (`/api/rfq/[id]/select`):
   - آن پیشنهاد `selected` و بقیه `rejected` می‌شوند.
   - وضعیت RFQ به `in_progress` می‌رود و از همهٔ لیست‌های عمومی حذف می‌شود
     (چون همهٔ کوئری‌های لیست، فیلتر `status:'active'` دارند).
   - از همین لحظه، اطلاعات تماس فروشندهٔ برنده در اختیار خریدار قرار می‌گیرد.
4. **تأیید دوطرفهٔ تحویل** (`/api/rfq/[id]/delivery`): هم خریدار هم فروشنده
   باید تأیید بزنند؛ با تأیید هر دو، RFQ به `completed` می‌رود. فعلاً هیچ
   واریز/تسویهٔ مالی در این مرحله انجام نمی‌شود.

## استراتژی سئو (سطح جهانی)

- **Metadata API نیتیو Next.js** در همهٔ صفحات: `title`, `description`,
  `canonical`, `openGraph`, `twitter` — هرکدام داینامیک بر اساس محتوای
  واقعی صفحه (نه متن ثابت).
- **صفحات پویا با SEO اختصاصی**: هر RFQ و هر دسته‌بندی `generateMetadata`
  مخصوص به خود دارد — این یعنی سئوی برنامه‌ای (programmatic SEO) روی هزاران
  صفحهٔ محصول/درخواست، دقیقاً همان کاری که رقبای بزرگ B2B (Alibaba,
  ThomasNet) انجام می‌دهند.
- **Structured Data (JSON-LD)**: `Organization` و `WebSite` در layout اصلی
  (برای Sitelinks Search Box در گوگل)، `Product`/`AggregateOffer` روی هر
  صفحهٔ RFQ.
- **`sitemap.ts` و `robots.ts` پویا**: بر اساس دیتای واقعی ساخته می‌شوند،
  نه فایل استاتیک — همیشه با محتوای زنده هم‌خوان‌اند.
- **RFQهای بسته‌شده `noindex` می‌شوند** ولی از سایت پاک نمی‌شوند (لینک‌های
  داخلی و history حفظ می‌شود) — از افت رتبهٔ ناشی از محتوای «مرده» جلوگیری
  می‌کند بدون از دست دادن equity لینک.
- **عملکرد**: فونت با `next/font` (بدون layout shift)، تصاویر با
  `next/image` (AVIF/WebP)، هدرهای کش برای فایل‌های استاتیک، فشرده‌سازی،
  HSTS و هدرهای امنیتی در `next.config.js` — Core Web Vitals و اعتماد
  مرورگر هر دو روی رتبه اثر دارند.
- **دسترس‌پذیری**: HTML معنایی (`<nav>`, `<dl>`, `<table>`)، `focus-visible`
  در همه‌جا، `prefers-reduced-motion` رعایت‌شده — این‌ها هم به‌طور غیرمستقیم
  روی سئو و هم روی نرخ ماندگار کاربر اثر دارند.
- **آماده برای بین‌المللی‌سازی**: `alternates.languages` و `x-default` در
  layout از حالا ست شده. برای افزودن انگلیسی، پیشنهاد من استفاده از
  `next-intl` با روت‌های `/en` و `/fa` و `hreflang` کامل بین دو نسخه است —
  ساختار فعلی برای این مهاجرت آماده نوشته شده (تمام متن‌ها در کامپوننت،
  نه در منطق).

## نقشه کامل صفحات ساخته‌شده

**عمومی:** `/` `/rfq` `/rfq/[slug]` `/rfq/new` `/categories` `/categories/[slug]`
`/sellers` `/how-it-works` `/about` `/faq` `/contact` `/terms` `/privacy` `/blog`

**احراز هویت:** `/login` `/register`

**خریدار (پروفایل):** `/profile` (نمای کلی) `/profile/rfqs` (تاریخچه
درخواست‌ها) `/profile/bids` (تاریخچه پیشنهادهای دریافتی) `/profile/settings`

**فروشنده:** `/seller` (داشبورد + درخواست‌های باز برای پیشنهاد‌دادن)

**ادمین:** `/admin` (آمار کلی) `/admin/rfqs` `/admin/users`
`/admin/categories` `/admin/settings`

**API (منطق اصلی کسب‌وکار):**
`GET/POST /api/rfq/[id]/bids`, `POST /api/rfq/[id]/select`,
`POST /api/rfq/[id]/delivery`

همه‌ی این صفحه‌ها فعلاً با دیتای mock کار می‌کنند (`lib/mock-data.ts` و
`lib/mock-admin-data.ts`) تا بدون دیتابیس هم قابل مشاهده و تست باشند؛
جایگزینی با کوئری واقعی مونگو فقط نیاز به عوض‌کردن منبع دیتا در همان
فایل‌های صفحه دارد — مدل‌ها و ایندکس‌ها از قبل آماده‌اند.

## نکاتی که باید بعداً اضافه شوند

- تأیید شماره موبایل (OTP) در کنار ایمیل/رمز عبور.
- آپلود تصویر واقعی برای آگهی‌ها (فیلد `images` در مدل `Rfq` از قبل هست).
- ویرایش نام/استان/شهر در تنظیمات حساب (فرم موجود است، فقط submit به
  Server Action وصل نشده).
- در آینده، در صورت نیاز: ماژول پرداخت/کیف‌پول (به‌صورت جدا و اختیاری).

## به‌روزرسانی چیدمان صفحه اصلی

صفحه اصلی از حالت سه‌ستونه (ستون‌های باریک راست/چپ که همه‌چیز را کوچک
می‌کرد) به یک صفحه‌ی تک‌ستونه و استاندارد تغییر کرد: هر بخش (دسته‌بندی‌ها،
مزایده‌های فعال، آمار پلتفرم، فعالیت اخیر، برترین فروشندگان، اطلاعیه‌ها،
چطور کار می‌کند) الان یک سکشن مجزا و تمام‌عرض است که با اسکرول پایین
می‌آید. هدر هم به دو ردیف تقسیم شد: ردیف اصلی (لوگو، جستجو، ورود/پروفایل)
و ردیف ناوبری (لینک‌های اصلی + میان‌بر دسته‌بندی‌ها).

اگر قبلاً `npm run seed` زده‌اید، دوباره بزنید تا ۲۲ دسته‌بندی کامل هم به
دیتابیس اضافه شود:

```bash
npm run seed
```

## رفع خطای E11000 duplicate key (phone_1)

اگر هنگام ثبت‌نام خطای `E11000 duplicate key error ... index: phone_1`
دیدید، یعنی روی دیتابیس واقعی‌تان یک ایندکس قدیمی و یکتا (`unique`) روی
فیلد `phone` از قبل وجود دارد — این ایندکس در مدل فعلی تعریف نشده است.

راه‌حل سریع در MongoDB Shell / Compass:
```js
use pelleh
db.users.dropIndex("phone_1")
```

راه‌حل دائمی: کافی است دوباره seed را اجرا کنید؛ حالا این اسکریپت پیش از
پر کردن داده، `syncIndexes()` را روی هر مدل صدا می‌زند و هر ایندکس
ناهم‌خوان با schema فعلی (مثل همین `phone_1`) را خودش حذف می‌کند:
```bash
npm run seed
```

## پنل ادمین کامل شد

- **دسته‌بندی‌ها** (`/admin/categories`): فرم افزودن دسته‌بندی جدید (با
  انتخاب آیکون از لیست lucide)، ویرایش inline، حذف (با جلوگیری از حذف
  دسته‌بندی‌ای که هنوز درخواست فعال دارد).
- **کاربران** (`/admin/users`): تایید/لغو تایید هویت، مسدود/رفع مسدودی
  حساب با یک کلیک. کاربر مسدود‌شده در لاگین بعدی رد می‌شود و اگر همان
  لحظه لاگین باشد، در اولین دسترسی به صفحات محافظت‌شده بیرون می‌رود.
- **درخواست‌های خرید** (`/admin/rfqs`): فیلتر بر اساس وضعیت، امکان لغو
  دستی هر درخواست فعال یا در حال انجام.
- **داشبورد** (`/admin`): علاوه بر کارت‌های آماری، حالا نمودار روند ثبت
  درخواست در ۱۴ روز اخیر، توزیع وضعیت درخواست‌ها، دسته‌بندی‌های پرتقاضا،
  و توزیع نقش کاربران را هم نشان می‌دهد — همه با کامپوننت‌های نموداری
  سبک و بدون کتابخانه‌ی خارجی جدید (تا ریسک نصب پکیج صفر بماند).

همه‌ی این اکشن‌ها Server Action هستند و پشت `requireAdmin()` قرار دارند؛
یعنی حتی اگر کسی مستقیم درخواست بفرستد، بدون نشست ادمین معتبر رد می‌شود.

## عکس بنر اصلی (Hero)

کد الان منتظر یک فایل در این مسیر است:

```
public/hero-illustration.png
```

- **فرمت:** ترجیحاً PNG با پس‌زمینه‌ی شفاف (روی گرادینت بنر می‌نشیند و جعبه‌ای دیده نمی‌شود). اگر عکس شما پس‌زمینه‌ی شفاف ندارد، JPG یا WebP هم کار می‌کند.
- **ابعاد:** مستطیل پهن با نسبت ۲ به ۱ (پهن‌تر از قبل، طولش زیاد می‌شود ولی ارتفاعش تقریباً همان می‌ماند — تا نزدیک متن «به پله خوش آمدید» بنشیند و حالت پوستری/بنری داشته باشد) — دقیقاً همان چیزی که در کد به صورت `aspect-[2/1]` تنظیم شده. حداکثر عرض نمایش ۳۲rem (۵۱۲ پیکسل) است، یک عدد ثابت برای همه‌ی سایزهای صفحه (نه یک نردبان جداگانه برای موبایل/دسکتاپ).
  فایل را با سایز **۱۶۰۰×۸۰۰ پیکسل** بسازید (نسبت ۲:۱ دقیق). چون نمایش با `object-contain` داخل یک باکس تا حداکثر ۵۱۲×۲۵۶ پیکسل انجام می‌شود، ۱۶۰۰×۸۰۰ هم کیفیت روی صفحه‌های retina را تضمین می‌کند و هم دقیقاً هم‌نسبت با باکس است — نیازی به برش یا کشیده‌شدن ندارد.
- **محتوای پیشنهادی:** یک ایلوستریشن یا رندر مرتبط با مزایده/تأمین کالا، هماهنگ با هویت نارنجی-شتری برند.
- فقط کافی است فایل را دقیقاً با همین نام در پوشه‌ی `public/` بریزید؛ کد از قبل به آن اشاره می‌کند.

## سیستم سه‌فونتی

پروژه از قبل برای سه فونت جدا آماده‌سازی شده — الان هر سه موقتاً روی
فونت گوگل «Vazirmatn» ست شده‌اند تا وقتی فونت نهایی انتخاب شود. هر سه
با `next/font` بارگذاری می‌شوند (بدون layout shift) و همه‌جای پروژه
از قبل به آن‌ها وصل است — با گذاشتن فایل درست، بدون هیچ تغییر دیگری در
کد، کل سایت فونت جدید می‌گیرد:

| فونت | نقش | کجا استفاده می‌شود | کلاس Tailwind |
|---|---|---|---|
| **Heading** | عنوان‌ها | تمام `h1` تا `h4` به‌صورت خودکار (بدون نیاز به کلاس دستی) | `font-heading` |
| **Body** | متن معمولی | پاراگراف‌ها، دکمه‌ها، لیبل‌ها، منو — پیش‌فرض کل سایت | `font-sans` / `font-body` |
| **Numeral** | اعداد | قیمت‌ها، شماره تلفن، تاریخ، هر جای دیگری که کلاس `.num` گرفته | `font-numeral` / `.num` |

برای وصل‌کردن فونت واقعی:

1. فایل فونت را (ترجیحاً فرمت `woff2` — سبک‌ترین و پشتیبانی‌شده‌ترین فرمت روی وب) با همین نام‌ها در پوشه‌ی `public/fonts/` بگذارید:
   ```
   public/fonts/heading.woff2
   public/fonts/body.woff2
   public/fonts/numeral.woff2
   ```
   اگر فایل شما فرمت دیگری دارد (مثلاً `ttf` یا `otf`)، همان را با همین اسم‌ها بگذارید و فقط بگویید تا پسوند را در کد یک‌خطی اصلاح کنم.
2. اگر برای یک فونت هم نسخه‌ی Regular و هم Bold دارید، هر دو را بگذارید (مثلاً `body.woff2` و `body-bold.woff2`) و بگویید — کد را طوری وصل می‌کنم که ضخیم‌شدن متن واقعی باشد نه شبیه‌سازی مرورگر.
3. می‌توانید هر سه را یک فونت یکسان بگذارید (اگر فقط یک فونت دلخواه دارید) یا سه فونت متفاوت — هر دو حالت با همین ساختار کار می‌کند.
4. بعد از گذاشتن فایل‌ها بگویید تا `app/layout.tsx` را از فونت گوگل موقت به این فایل‌های محلی سوییچ کنم (این تغییر را الان انجام نمی‌دهم چون تا وقتی فایل واقعی سر جایش نباشد، build با خطا مواجه می‌شود).

## دسته‌بندی‌های دو سطحی (والد/زیردسته)

ساختار دسته‌بندی از یک لیست تخت به یک درخت دو سطحی تغییر کرد — ۱۲ دسته
اصلی (وسایل الکترونیکی، وسایل نقلیه، صنعتی و کارگاهی، ابزار و یراق،
ساختمانی و مصالح، خوراکی و کشاورزی، تزئینی و دکوراسیون، کودک و نوزاد،
پوشاک و مد، اداری و تجاری، سلامت و پزشکی، ورزش و سرگرمی) که هرکدام ۴ تا ۶
زیردسته دارند. تعریف کامل این درخت در `lib/category-tree.ts` است.

مدل `Category` از قبل فیلد `parent` را داشت، فقط استفاده نمی‌شد؛ الان
هم seed و هم همه‌ی صفحات (صفحه اصلی، هدر، فوتر، `/categories`،
`/categories/[slug]`، فرم ثبت درخواست خرید، پنل ادمین) از این ساختار
دوسطحی می‌خوانند. برای اعمال این تغییر روی دیتابیس‌تان:

```bash
npm run seed
```

توجه: seed تمام داده‌های قبلی (کاربران، درخواست‌ها، دسته‌بندی‌های تخت
قبلی) را پاک و از نو با ساختار جدید می‌سازد. اگر داده‌های دستی دیگری در
دیتابیس دارید که نمی‌خواهید پاک شود، seed را دستی ویرایش کنید یا
دسته‌بندی‌های جدید را از پنل ادمین (`/admin/categories`) اضافه کنید —
آنجا هم انتخاب دسته‌ی والد را دارد.

## ترتیب جدید صفحه اصلی

بنر → پله چطور کار می‌کند → دسته‌بندی‌های محبوب → مزایده‌های فعال →
فعالیت‌های اخیر پلتفرم → برترین فروشندگان → اطلاعیه‌ها → فوتر.

بخش‌های «آمار کلی پلتفرم» و «درخواست‌های خرید اخیر (جدول)» از صفحه اصلی
حذف شدند (چون در ترتیب درخواستی نبودند)؛ اگر دوست دارید یکی از آن‌ها
برگردد، بگویید کجای این ترتیب جایش بدهم.

## سیستم اعتبارسنجی و اخطار فروشندگان (ضد پیشنهاد الکی)

### مدال شرایط برای فروشندگان جدید
هر فروشنده‌ای که وارد سایت شود و هنوز شرایط را نپذیرفته باشد، در **هر
صفحه‌ای** (چون این چک در `Header` قرار دارد که همه‌جا رندر می‌شود) با یک
مدال تمام‌صفحه و غیرقابل‌بستن روبه‌رو می‌شود که توضیح می‌دهد:
- روند مزایده چطور کار می‌کند
- آستانه‌ی قیمت مشکوک (زیر ۷۰٪ میانگین سایر پیشنهادها)
- تعهد ۵ روزه برای تایید تحویل پس از برد
- سیستم اخطار سه‌مرحله‌ای

فقط با تیک‌زدن «پذیرفتم» و زدن دکمه‌ی «مرحله بعد» مدال بسته می‌شود
(`sellerTermsAcceptedAt` در دیتابیس ثبت می‌شود). تا وقتی نپذیرفته، حتی
اگر مستقیم درخواست API برای ثبت پیشنهاد بفرستد، سرور رد می‌کند (چک در
خود `POST /api/rfq/[id]/bids` هم هست، نه فقط در UI).

### تشخیص قیمت مشکوک (خودکار)
هر بار سلر پیشنهاد ثبت می‌کند، قیمتش با میانگین سایر پیشنهادهای *باز*
همان درخواست مقایسه می‌شود. اگر کمتر از **۷۰٪ میانگین** باشد، بلافاصله
یک اخطار برایش ثبت می‌شود (`lib/violations.ts` → `checkSuspiciousBid`).

### تشخیص عدم تحویل (خودکار)
وقتی خریدار یک پیشنهاد را انتخاب می‌کند، `rfq.selectedAt` ثبت می‌شود. اگر
تا **۵ روز** بعد فروشنده تحویل را تایید نکند، یک اخطار خودکار ثبت
می‌شود. این چک به‌صورت فرصت‌طلبانه («opportunistic») هم روی خودِ صفحه‌ی
آن درخواست، و هم به‌صورت یک sweep کلی روی همه‌ی درخواست‌های `in_progress`
هر بار پنل ادمین باز می‌شود اجرا می‌شود — چون این محیط cron/job واقعی
ندارد. **برای پروداکشن واقعی، پیشنهاد می‌کنم این sweep را به‌جای اتکا به
بازدید ادمین، با یک cron job واقعی (مثلاً Vercel Cron یا یک worker جدا)
هر چند ساعت یک‌بار اجرا کنید** — تابعش (`sweepOverdueDeliveries`) از قبل
آماده و مستقل است، فقط باید از یک زمان‌بند صدا زده شود.

### گزارش خریدار (نیازمند تایید ادمین)
خریدار می‌تواند از صفحه‌ی درخواست خودش، دکمه‌ی «گزارش عدم تحویل فروشنده»
را بزند. برخلاف دو مورد بالا، این یکی **خودکار اخطار نمی‌دهد** — چون
موضوعی و قابل‌مناقشه است — بلکه مستقیم به صف بررسی ادمین می‌رود.

### سیستم اخطار سه‌مرحله‌ای
- **اخطار ۱:** خودکار. فروشنده از فهرست «برترین فروشندگان» به مدت ۷ روز
  حذف می‌شود.
- **اخطار ۲:** خودکار. حساب به مدت ۱۴ روز تعلیق می‌شود (`tempSuspendedUntil`)
  — در این مدت لاگین و فعالیت مسدود است، بعد از تاریخ خودکار برمی‌گردد.
- **اخطار ۳ به بعد:** **هرگز خودکار بن نمی‌شود.** حساب با فلگ
  `banReviewPending` علامت می‌خورد و پرونده در
  `/admin/violations` (با نشان‌گر تعداد روی نوار کناری ادمین) منتظر
  تصمیم دستی می‌ماند. ادمین می‌تواند «بن دائم» یا «رد گزارش» بزند.

### فایل‌های کلیدی این سیستم
- `models/SellerViolation.ts` — رکورد هر تخلف
- `lib/violations.ts` — همه‌ی منطق (آستانه‌ها، اعمال اخطار، تشخیص)
- `components/SellerTermsModal.tsx` + `app/seller/actions.ts` — مدال پذیرش شرایط
- `app/admin/violations/` — صف بررسی ادمین
- فروشندگان seed‌شده (`seller1@pelleh.ir` و بقیه) عمداً `sellerTermsAcceptedAt`
  ندارند تا بلافاصله بعد از لاگین بتوانید مدال را ببینید و تست کنید.

## رفع خطای Runtime: `querySrv ECONNREFUSED _mongodb._tcp....mongodb.net`

### علت این خطا چیست؟

این خطا از ماژول `dns` خودِ Node.js میاد، **نه از کد این پروژه**. وقتی
`MONGODB_URI` از نوع `mongodb+srv://` باشد (که استاندارد Atlas است)،
درایور MongoDB قبل از هر اتصالی باید یک **DNS SRV lookup** انجام دهد
(`_mongodb._tcp.<cluster>`) تا لیست واقعی سرورهای cluster را بگیرد.
`ECONNREFUSED` یعنی خودِ این پرس‌وجوی DNS رد شده — یعنی مشکل قبل از
رسیدن به MongoDB Atlas، در لایه‌ی شبکه/DNS سیستم شماست:

- فایروال، آنتی‌ویروس، یا VPN (خصوصاً split-tunnel) پرس‌وجوهای DNS از
  نوع SRV را مسدود می‌کند.
- شبکه‌ی محل کار/دانشگاه این نوع پرس‌وجو را مسدود می‌کند.
- روی WSL یا Docker هستید و DNS داخل آن محیط با شبکه‌ی هاست هماهنگ نیست.
- Node.js پرس‌وجوهای DNS را مستقیم به نیم‌سرورهای پیکربندی‌شده می‌فرستد
  (نه از طریق resolver کامل سیستم‌عامل)، پس ممکن است مرورگر اینترنت
  داشته باشد ولی Node در همین یک نوع پرس‌وجو گیر کند.

### قدم اول: اجرای تست مستقل

```bash
npm run test:db
```

این اسکریپت (`scripts/test-db-connection.ts`) کاملاً مستقل از Next.js
است و سه چیز را جدا تست می‌کند: فرمت `MONGODB_URI`، خودِ DNS SRV lookup،
و اتصال واقعی Mongoose. نتیجه‌اش دقیقاً مشخص می‌کند مشکل کجاست.

### راه‌حل‌ها (به ترتیب توصیه)

**۱. استفاده از connection string غیر-SRV (معمولاً بهترین راه‌حل دائمی)**
اگر شبکه‌ی شما به‌طور مداوم SRV lookup را مسدود می‌کند، Atlas خودش یک
فرمت جایگزین رسمی ارائه می‌دهد که هیچ SRV lookup نیاز ندارد (لیست
هاست‌ها مستقیم در خودِ URI هست):
از داشبورد Atlas → Connect → Drivers → گزینه‌ی
"I'm not able to connect due to firewall / DNS" یا نسخه‌ی قدیمی‌تر
درایور را انتخاب کنید تا یک URI با فرمت
`mongodb://host1,host2,host3/...?ssl=true&replicaSet=...&authSource=admin`
بگیرید. این را به‌جای مقدار فعلی در `MONGODB_URI` بگذارید — هیچ تغییر
کدی لازم نیست، چون `lib/mongodb.ts` هر دو فرمت را بدون تغییر می‌پذیرد.

**۲. تغییر موقت DNS resolver (فقط برای dev، فقط با env var صریح)**
اگر می‌خواهید فرمت SRV را نگه دارید، می‌توانید Node را موقتاً به یک
DNS عمومی قابل‌اعتماد (Cloudflare/Google) هدایت کنید:
```
MONGODB_DNS_SERVERS=1.1.1.1,8.8.8.8
```
این را در `.env.local` بگذارید. **این تغییر فقط وقتی فعال می‌شود که
خودتان صریحاً این متغیر را ست کنید** — به‌صورت پیش‌فرض هیچ تغییری در
تنظیمات DNS سیستم شما ایجاد نمی‌شود (`lib/mongodb.ts` را ببینید).

**۳. بررسی فایروال/آنتی‌ویروس/VPN محلی**
اگر هیچ‌کدام از بالا جواب نداد، مشکل قطعاً یک نرم‌افزار امنیتی یا
پیکربندی شبکه‌ی محلی است که پرس‌وجوهای UDP:53 از نوع SRV را می‌بندد؛
باید در تنظیمات همان نرم‌افزار بررسی شود.

### چه چیزی در کد پروژه اصلاح شد؟

`lib/mongodb.ts` یک باگ واقعی داشت که این خطا را بدتر می‌کرد: وقتی
اولین تلاش اتصال fail می‌شد (دقیقاً مثل این خطای DNS)، Promise
rejected‌شده در cache می‌ماند و **تمام درخواست‌های بعدی، بدون تلاش
مجدد، بلافاصله همان خطای قدیمی را دوباره پرتاب می‌کردند** — حتی بعد از
رفع مشکل شبکه، تا زمانی که سرور dev را ری‌استارت می‌کردید. این الان
اصلاح شده: با هر شکست، cache پاک می‌شود تا درخواست بعدی دوباره تلاش کند.
همچنین `serverSelectionTimeoutMS` و `connectTimeoutMS` صریح (۱۰ ثانیه)
اضافه شد تا در صورت مشکل شبکه، خطا سریع‌تر و قابل‌پیش‌بینی‌تر ظاهر شود
به‌جای معلق ماندن طولانی.

## پنج اصلاح این دور

### ۱. نمایش خطای لاگین/ثبت‌نام روی خود صفحه
قبلاً خطاها (`throw new Error(...)`) به‌جای نمایش دوستانه، به کرش
عمومی Next.js می‌رفتن. الان `app/(auth)/actions.ts` به‌جای throw کردن،
یک `{ error: string }` برمی‌گرداند و فرم‌ها (`LoginForm.tsx`,
`RegisterForm.tsx`) با `useFormState` از `react-dom` این پیام را مستقیم
زیر فرم نشان می‌دهند — شامل «ایمیل قبلاً ثبت شده»، «ایمیل یا رمز عبور
اشتباه است»، و پیام مخصوص قطعی اتصال («خطا در اتصال به سرور...») وقتی
مشکل از دیتابیس/شبکه باشد، نه از ورودی کاربر.

### ۲. ورود/ثبت‌نام با گوگل
دکمه‌ی «ورود با گوگل» به هر دو صفحه اضافه شد. پیاده‌سازی با fetch
مستقیم به endpoint های خودِ گوگل انجام شده (بدون افزودن هیچ پکیج جدید
npm، برای اینکه ریسک نصب اضافه نشود). برای فعال‌سازی واقعی، سه متغیر
env را طبق راهنمای داخل `.env.example` پر کنید (`GOOGLE_CLIENT_ID`,
`GOOGLE_CLIENT_SECRET`، و redirect URI دقیق در Google Cloud Console).
**نکته مهم:** چون صفحه‌ی رضایت گوگل جایی برای انتخاب «خریدار یا
فروشنده» ندارد، کاربر تازه‌واردی که با گوگل ثبت‌نام کند پیش‌فرض
**خریدار** ثبت می‌شود. اگر لازم دارید فروشنده باشد، فعلاً باید با
ایمیل/رمز عادی ثبت‌نام کند و «فروشنده» را انتخاب کند.

### ۳. دکمه‌ی بنر برای فروشنده کار نمی‌کرد
`components/Hero.tsx` مقصد دکمه را هاردکد به `/rfq/new` داشت که مخصوص
خریدار است؛ فروشنده کلیک می‌کرد و middleware بی‌صدا به صفحه‌ی اصلی
برش می‌گرداند. الان دقیقاً مثل دکمه‌ی هدر، بر اساس نقش تعیین می‌شود:
مهمان → `/rfq/new` با متن «ثبت درخواست خرید یا فروش»، خریدار →
`/rfq/new` با متن «ثبت درخواست خرید»، فروشنده → `/seller` (داشبورد
فروشنده، جایی که واقعاً می‌تواند قیمت زیر درخواست‌ها ثبت کند) با متن
«ثبت درخواست فروش».

### ۴. دکمه‌ی خروج (Logout) روی سایت
یک آیکون خروج کنار نام/آواتار کاربر در هدر (`components/Header.tsx`)
اضافه شد — قبلاً فقط از داخل تنظیمات پروفایل قابل خروج بود.

### ۵. پنل ادمین با نام‌کاربری/رمز عبور جدا در env، مستقل از کاربران عادی
این بزرگ‌ترین تغییر این دور بود. خلاصه‌ی معماری جدید:

- **دو تا `.env.local` جدید:** `ADMIN_USERNAME` و `ADMIN_PASSWORD`.
- آدرس `/admin` برای همه باز است (کسی بر اساس IP/مرورگر مسدود نمی‌شود)
  — ولی بدون سشن معتبر ادمین، مستقیم به `/admin/login` هدایت می‌شود.
- `/admin/login` یک فرم کاملاً جدا دارد که فقط این دو مقدار env را
  چک می‌کند — **هیچ ربطی به جدول کاربران MongoDB و ایمیل/رمز عادی
  سایت ندارد.** یعنی «کدام ایمیل روی مرورگر لاگین است» دیگر هیچ نقشی
  در دسترسی به پنل ادمین ندارد.
- ساختار پوشه‌ها تغییر کرد: تمام صفحات محافظت‌شده‌ی ادمین به
  `app/admin/(protected)/` منتقل شدند (یک Route Group — این پرانتز در
  خودِ URL ظاهر نمی‌شود، `/admin`، `/admin/users` و بقیه دقیقاً همان
  آدرس‌های قبلی می‌مانند) تا `layout.tsx` محافظ فقط روی صفحات واقعی
  ادمین اعمال شود، نه روی خودِ فرم لاگین (وگرنه یک حلقه‌ی بی‌نهایت
  ریدایرکت پیش می‌آمد).
- `middleware.ts` و `lib/require-admin.ts` (که همه‌ی Server Action های
  ادمین از آن استفاده می‌کنند) هر دو به این سشن جدید وصل شدند.
- یک دکمه‌ی «خروج از پنل ادمین» جدا هم به سایدبار پنل اضافه شد — چون
  این یک سشن کاملاً مستقل از سشن کاربری عادی است.
- **پیامد فرعی این تغییر:** فیلد `reviewedBy` روی پرونده‌های تخلف
  (کدام ادمین یک تخلف را تایید/رد کرده) دیگر پر نمی‌شود، چون ادمین
  دیگر یک رکورد کاربر در دیتابیس نیست که شناسه‌ی معتبری داشته باشد.
  زمان تصمیم (`reviewedAt`) هنوز ثبت می‌شود.

برای ورود به پنل ادمین اکنون:
```
https://یا-localhost:3000/admin
```
و در فرمی که باز می‌شود، همان `ADMIN_USERNAME`/`ADMIN_PASSWORD` که در
`.env.local` گذاشته‌اید را وارد کنید — نه ایمیل حساب `admin@pelleh.ir`
که قبلاً از seed می‌آمد (آن حساب برای منطق دیگری در سیستم، مثل
`role: "admin"` روی مدل کاربر، هنوز در دیتابیس هست ولی دیگر راهی برای
ورود به پنل ادمین از طریق آن وجود ندارد).

## سوییچ نقش خریدار ↔ فروشنده

چون ورود با گوگل جایی برای انتخاب «خریدار یا فروشنده» ندارد و همیشه
پیش‌فرض خریدار ثبت می‌شود، یک گزینه‌ی «تغییر به فروشنده / تغییر به
خریدار» به `/profile/settings` اضافه شد (`SwitchRoleButton.tsx` +
`switchRoleAction`). این کار:

- نقش کاربر را در دیتابیس عوض می‌کند،
- سشن (کوکی) را بلافاصله با نقش جدید دوباره صادر می‌کند — بدون این
  کار، نقش قدیمی تا لاگین بعدی در JWT می‌ماند و همه‌ی چک‌های نقش در
  سایت (middleware، هدر، مالکیت درخواست‌ها) را گیج می‌کرد،
- کاربر را به داشبورد متناسب با نقش جدید (`/` یا `/seller`) می‌فرستد.

اگر کاربری برای اولین‌بار فروشنده شود، همان مدال شرایط فروشنده
(`SellerTermsModal`) که قبلاً ساختیم خودکار برایش ظاهر می‌شود — چون آن
مدال فقط بر اساس `sellerTermsAcceptedAt` تصمیم می‌گیرد، نه اینکه
کاربر از ابتدا فروشنده بوده یا تازه سوییچ کرده.

این گزینه برای حساب‌های ادمین نمایش داده نمی‌شود.

## بخش پیشنهادات و انتقادات کاربران

- **صفحه‌ی عمومی:** `/suggestions` (لینکش در فوتر، بخش «پشتیبانی» هم
  اضافه شد). هرکسی می‌تواند بفرستد — چه لاگین باشد چه نباشد:
  - اگر لاگین باشد، نام/ایمیل/نقش/شناسه‌ی کاربری‌اش **خودکار و از
    سشن واقعی** گرفته می‌شود (نه از چیزی که در فرم تایپ می‌کند — پس
    قابل جعل نیست).
  - اگر لاگین نباشد، خودش نام (و اختیاری ایمیل) را تایپ می‌کند.
- **پنل ادمین:** `/admin/suggestions` — لیست کامل پیام‌ها با نام،
  ایمیل، نقش فرستنده و زمان ارسال؛ دکمه‌ی «علامت به‌عنوان خوانده‌شده»
  و «حذف». تعداد پیام‌های خوانده‌نشده هم به‌صورت یک نشان قرمز روی
  «پیشنهادات کاربران» در نوار کناری پنل ادمین نمایش داده می‌شود
  (دقیقاً مثل نشان پرونده‌های تخلف).
- مدل داده: `models/Suggestion.ts`.
